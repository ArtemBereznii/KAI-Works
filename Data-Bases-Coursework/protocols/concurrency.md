# Протокол конкурентного доступу (BR11)

> **Цей сценарій виконує здобувач особисто у двох окремих сеансах psql.** Поля «Фактичний результат» заповнюються лише тим, що з'явилося на екрані: час очікування, номери процесів, повідомлення. Не підставляйте очікувані значення.

**Виконавець:** ____ · **Дата:** ____ · **СУБД:** PostgreSQL 18.7 (контейнер `transit-pg`) · **Рівень ізоляції:** READ COMMITTED (за замовчуванням)

## Мета

Перевірити, що два одночасні списання з однієї картки не призводять до «подвійної витрати». Картка 4777000000000001 має баланс 30.00: цього вистачає на одну поїздку автобусом (20.00), але не на дві. Якби процедура читала баланс без блокування, обидва сеанси побачили б 30.00 і обидва списали б по 20.00. Тоді або один зі списань «загубився б» (lost update), або друга транзакція впала б на `CHECK (balance >= 0)` уже після перевірки коштів.

Механізм захисту: `proc_register_trip` на початку виконує `SELECT … FROM cards WHERE card_number = … FOR UPDATE`. Другий сеанс чекає на цьому рядку до завершення першої транзакції, а потім читає вже оновлений баланс.

## Підготовка

```sh
./run_all.sh                              # чистий стан
./run_all.sh concurrency_setup.sql        # картка 4777000000000001, баланс 30.00
```

Відкрийте **два окремі термінали** (не дві вкладки одного psql) і в кожному запустіть:

```sh
docker compose exec db psql -U postgres -d transit_db
```

Переконайтеся, що це різні підключення: номери процесів у двох вікнах мають відрізнятися.

```sql
SELECT pg_backend_pid();
SET search_path = transit, public;
SET ROLE transit_validator;     -- дія від імені валідатора, а не власника
```

## Порядок команд

Обидва сеанси працюють з **одним і тим самим валідатором** V-10001. Повторна валідація на тому самому валідаторі — це оплата за ще одного пасажира, а не пересадка (BR10), тому друга поїздка теж має бути платною.

| Крок | Сеанс А | Сеанс Б | Очікувано |
|---|---|---|---|
| 1 | `BEGIN;` | | |
| 2 | `CALL proc_register_trip('4777000000000001', 'V-10001', NULL, NULL, NULL, NULL);` | | А: `balance`, списано 20.00, баланс 10.00. Транзакція відкрита, рядок картки заблоковано |
| 3 | | `BEGIN;` | |
| 4 | | `SET LOCAL lock_timeout = '60s';` | |
| 5 | | `CALL proc_register_trip('4777000000000001', 'V-10001', NULL, NULL, NULL, NULL);` | Б **зависає**: чекає на блокування рядка картки |
| 6 | *(третій сеанс, необов'язково)* `SELECT pid, wait_event_type, wait_event, state, left(query, 60) FROM pg_stat_activity WHERE datname = 'transit_db' AND state <> 'idle';` | | Сеанс Б: `wait_event_type = Lock`, `wait_event = transactionid` |
| 7 | `COMMIT;` *(протягом 60 с після кроку 5)* | | А: зміни зафіксовано |
| 8 | | *(продовжується автоматично)* | Б: `ERROR: BR02: недостатньо коштів на картці 4777000000000001 (баланс 10.00, потрібно 20.00)` |
| 9 | | `ROLLBACK;` | |
| 10 | `RESET ROLE;` `SELECT balance FROM cards WHERE card_number = '4777000000000001';` і `SELECT count(*) FROM trips t JOIN cards c ON c.id = t.card_id WHERE c.card_number = '4777000000000001';` | | баланс 10.00, поїздок 1 |

Якщо між кроками 5 і 7 минуло більше 60 с, у сеансі Б з'явиться `ERROR: canceling statement due to lock timeout`. Тоді виконайте `ROLLBACK;` у Б і `ROLLBACK;` або `COMMIT;` в А та повторіть сценарій після `./run_all.sh` і `concurrency_setup.sql`.

## Пояснення для записки

- **Межі транзакції.** Уся реєстрація поїздки (перевірка картки, вибір способу оплати, вставка в `trips` і `charges`, оновлення `cards.balance`) виконується в одній транзакції. Помилка на будь-якому кроці скасовує всі зміни (див. тест T15 у [tests.md](tests.md)).
- **Чому READ COMMITTED достатньо.** Конфлікт усуває явне блокування рядка `FOR UPDATE`, а не рівень ізоляції. Після зняття блокування PostgreSQL перечитує заблокований рядок, і сеанс Б бачить уже зафіксований баланс 10.00. На рівні SERIALIZABLE або REPEATABLE READ сеанс Б замість цього отримав би `could not serialize access due to concurrent update`, і застосунку довелося б повторювати транзакцію.
- **Атомарність, видимість і блокування — різні речі.** Поки сеанс А не виконав COMMIT, інші сеанси не бачать його поїздки (видимість), а сеанс Б не може змінити картку (блокування). Якби А виконав ROLLBACK замість COMMIT, Б продовжив би з балансом 30.00, і поїздка Б була б успішною.
- Блокування стосується лише однієї картки. Поїздки інших карток виконуються паралельно без очікування.
