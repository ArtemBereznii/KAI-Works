# Протокол дослідження продуктивності (EXPLAIN до/після)

**Дата вимірювання:** 22.11.2026 · **Скрипт:** `sql/09_perf.sql` · **Повний вивід:** [explain_run.txt](explain_run.txt) (без змін)

## Умови

| Показник | Значення |
|---|---|
| СУБД | PostgreSQL 18.7 (Docker-образ `postgres:18`, Debian), `shared_buffers = 128MB` |
| Середовище | Docker Desktop на Windows 10, той самий контейнер для всіх вимірювань |
| Таблиця `trips` | 501 323 рядки (1 323 з `06_seed.sql` + 500 000 згенерованих), heap 37 MB |
| Генерація | `09_perf.sql`: 2 000 анонімних карток, 18 000 місячних проїзних (поповнення → купівля), 500 000 поїздок за проїзними у випадкові моменти 01.01–28.09.2026 (`setseed(0.67)`), вставлені в порядку часу. Тривалість вставки поїздок — 15,6 с. Звірка балансу після генерації — 0 розбіжностей |
| Статистика | `ANALYZE` перед кожним станом; кореляція фізичного порядку з `validated_at` — 0,98 |
| Порядок | Перезапуск контейнера (порожній `shared_buffers`) → 3 запуски «до» → створення індексу → 3 запуски «після». Перший запуск фіксується окремо; кеш ОС у віртуальній машині Docker перезапуском не очищується, тому `read` означає читання поза буферами PostgreSQL, а не обов'язково з диска |

## E1. Усі поїздки за одну добу (вибірка за інтервалом часу)

```sql
SELECT count(*), count(DISTINCT card_id) FROM trips
WHERE validated_at >= '2026-05-12' AND validated_at < '2026-05-13';
```

Результат: 1 835 поїздок. Зміна: `CREATE INDEX trips_validated_at_brin ON trips USING brin (validated_at);`

| Показник | До зміни | Після зміни |
|---|---|---|
| Параметри | доба 12.05.2026 | ті самі |
| Основні вузли плану | Bitmap Index Scan по `trips_card_time_uq` (**skip scan**, `Index Searches: 737`) → Bitmap Heap Scan (exact = 18 сторінок) → Sort → Aggregate | Bitmap Index Scan по `trips_validated_at_brin` (`Index Searches: 1`) → Bitmap Heap Scan (lossy = 256 сторінок, `Rows Removed by Index Recheck: 25 693`) → Sort → Aggregate |
| Фактичні рядки / loops | 1 835 / 1 | 1 835 / 1 |
| Execution Time, запуск 1 | 24,349 ms | 3,568 ms |
| Execution Time, запуски 2 і 3 | 8,983 ms; 9,287 ms | 2,671 ms; 3,655 ms |
| Buffers, запуск 1 | shared hit = 1 465, read = 2 404 | shared hit = 133, read = 128 |
| Buffers, повторні | shared hit = 3 866 | shared hit = 258 |
| Вартість індексу | — | 24 kB |

**Пояснення.** Окремого індексу за часом не було, але планувальник PostgreSQL 18 не обрав послідовне сканування. Він використав наявний індекс `UNIQUE (card_id, validated_at)` з пропуском першого стовпця (skip scan): 737 окремих спусків по B-tree, по одному на кожне значення `card_id`. Це дешевше за Seq Scan, але змушує прочитати ~3,8 тис. сторінок індексу. BRIN зберігає мінімум і максимум `validated_at` для кожних 128 сторінок таблиці. Оскільки поїздки записуються в порядку часу, індекс одразу відсікає майже всю таблицю: читається 256 сторінок даних, а зайві рядки з цих сторінок (25 693) відкидає Recheck. Читання скоротилося з 3 866 до 258 буферів (у 15 разів), час — у 2,5–7 разів (7 — для першого запуску). Індекс займає 24 kB проти 15 MB у B-tree з наступного експерименту.

**Обмеження.** BRIN ефективний лише доти, доки фізичний порядок рядків збігається з часом (кореляція 0,98). Масове завантаження даних «за минулі дати» або `UPDATE` такого стовпця погіршать його. Для вибірки кількох рядків за точним моментом BRIN гірший за B-tree.

## E2. Навантаження одного валідатора за місяць

```sql
SELECT date_trunc('day', t.validated_at) AS day, count(*)
FROM trips AS t
WHERE t.validator_id = (SELECT id FROM validators WHERE code = 'V-40003')
  AND t.validated_at >= '2026-05-01' AND t.validated_at < '2026-06-01'
GROUP BY 1 ORDER BY 1;
```

Результат: 31 рядок (5 305 поїздок). Зміна: `CREATE INDEX trips_validator_time_idx ON trips (validator_id, validated_at);` (BRIN з E1 у цей момент уже існує).

| Показник | До зміни | Після зміни |
|---|---|---|
| Параметри | V-40003, травень 2026 | ті самі |
| Основні вузли плану | Bitmap Index Scan по `trips_card_time_uq` (skip scan, `Index Searches: 403`, 57 399 рядків-кандидатів) → Bitmap Heap Scan + `Filter: validator_id`, `Rows Removed by Filter: 52 094` → Sort → GroupAggregate | Bitmap Index Scan по `trips_validator_time_idx` (`Index Searches: 1`, 5 305 рядків) → Bitmap Heap Scan (exact = 537) → Sort → GroupAggregate |
| Фактичні рядки / loops | 5 305 / 1 у Heap Scan, 31 на виході | 5 305 / 1, 31 на виході |
| Execution Time, запуск 1 | 24,264 ms | 3,049 ms |
| Execution Time, запуски 2 і 3 | 18,708 ms; 19,935 ms | 2,822 ms; 2,815 ms |
| Buffers, запуск 1 | shared hit = 3 198, read = 601 | shared hit = 538, read = 23 |
| Buffers, повторні | shared hit = 3 799 | shared hit = 561 |
| Вартість індексу | — | 15 MB (≈ 40 % розміру таблиці) |

**Пояснення.** До зміни умова за валідатором перевірялась фільтром уже після вибірки всього місяця: 52 094 з 57 399 прочитаних рядків відкидалися. Складений індекс з рівністю на першому стовпці та діапазоном на другому повертає рівно потрібні 5 305 рядків за один спуск. Буферів стало в 6,8 раза менше, а повторний запуск прискорився приблизно в 7 разів.

**Ціна рішення.** 15 MB на 500 тис. рядків і додатковий запис в індекс при кожній валідації (`proc_register_trip`). Для системи, де вставок значно більше, ніж звітів, індекс доцільний лише за регулярної потреби в такому звіті. Альтернатива — матеріалізоване представлення з добовими підсумками за валідаторами.

## E0. Останні 10 поїздок картки (контрольний запит)

Індекс не додавався: запит уже обслуговує `trips_card_time_uq`, план — `Index Scan Backward`, Execution Time = 0,068 ms (16 буферів). Новий індекс `(card_id, validated_at DESC)` дублював би наявний унікальний, бо B-tree читається в обох напрямках.

## Висновки

1. Для вибірки за інтервалом часу в журналі, що поповнюється в хронологічному порядку, обрано **BRIN**: майже такий самий виграш, як дав би B-tree, при розмірі 24 kB.
2. Для звітів за валідатором обрано **складений B-tree** `(validator_id, validated_at)`: стовпець рівності — першим, діапазону — другим.
3. Без додаткових індексів PostgreSQL 18 вже уникав послідовного сканування завдяки skip scan по `(card_id, validated_at)`. Тому виграш за часом помірний (у 2,5–7 разів), а не на порядки, як очікувалося б для Seq Scan.
4. Абсолютні значення часу залежать від середовища (Docker на Windows, теплий кеш ОС). Висновки спираються передусім на кількість прочитаних буферів і на зміну вузлів плану.
