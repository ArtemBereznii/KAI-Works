# Курсова «Бази даних» — варіант 67: план виконання

**Тема (з розділу 9.17 методички):** «Проєктування та реалізація бази даних інформаційної системи електронних проїзних документів»
Зміст теми: пасажирські картки, тарифні плани, поповнення, поїздки та списання коштів.
**СУБД:** PostgreSQL (документація у методичці — версія 18). Демонстрація — psql / pgAdmin / DBeaver. GUI не потрібен, якщо його не вимагає завдання.

## 3. Запропонована модель (схема `transit`, ~12 таблиць)

| № | Таблиця | Призначення |
|---|---|---|
| 1 | `privilege_categories` | Пільги (студент, пенсіонер…) з % знижки |
| 2 | `passengers` | Власники персоналізованих карток (картка може бути анонімною) |
| 3 | `cards` | Картка: номер (UNIQUE, CHECK формату), статус, баланс `numeric(10,2) CHECK >= 0`, дати видачі/дії |
| 4 | `card_status_history` | Історія змін статусу (аудит, заповнює тригер) |
| 5 | `transport_types` | Автобус, тролейбус, трамвай, метро |
| 6 | `fares` | Вартість поїздки за видом транспорту з періодом дії; EXCLUDE на перетин періодів |
| 7 | `tariff_plans` | Тарифні плани: разова оплата / проїзний на період / пакет поїздок |
| 8 | `card_subscriptions` | Підключені до картки проїзні: період, залишок поїздок; EXCLUDE на перетин періодів |
| 9 | `validators` | Валідатори (код, маршрут/транспорт) |
| 10 | `top_ups` | Поповнення: сума, канал, `payment_ref UNIQUE` (ідемпотентність, ON CONFLICT) |
| 11 | `trips` | Поїздки (валідації): картка, валідатор, момент, UNIQUE(card_id, validated_at) |
| 12 | `charges` | Списання коштів: за поїздку або за купівлю тарифного плану, баланс після операції |

Нормалізація до 3НФ: ціни винесено у `fares` (а не в кожну поїздку), характеристики плану — у `tariff_plans`. Свідома денормалізація: `cards.balance` (кеш суми поповнень мінус списання) — обґрунтувати й підтримувати тільки процедурами + контрольний запит звірки з журналом.

## 4. Бізнес-правила (чернетка простежуваності)

| Код | Правило | Реалізація → перевірка |
|---|---|---|
| BR01 | Номер картки унікальний і має формат | UNIQUE + CHECK (regex) → дублікат / неправильний формат |
| BR02 | Баланс не може бути від'ємним | CHECK + перевірка в процедурі → поїздка без коштів |
| BR03 | Поповнення від 1 до 5000 грн | CHECK → 0 і 5001 (граничні) |
| BR04 | Заблокована/прострочена картка не проходить валідацію | BEFORE-тригер / процедура → спроба поїздки |
| BR05 | Дозволені лише визначені переходи статусу (active→blocked→active, active→lost — кінцевий) | BEFORE-тригер → lost→active |
| BR06 | Періоди дії тарифів одного виду транспорту не перетинаються | EXCLUDE USING gist (btree_gist) → перетин дат |
| BR07 | Проїзні однієї картки не перетинаються за періодом | EXCLUDE → другий проїзний на той самий місяць |
| BR08 | Картку з історією операцій не можна видалити | FK ON DELETE RESTRICT → DELETE |
| BR09 | Повторне поповнення з тим самим payment_ref не дублюється | UNIQUE + ON CONFLICT DO NOTHING → повтор платежу |
| BR10 | Безкоштовна пересадка протягом 60 хв (опційно, погодити) | Логіка процедури → дві валідації |
| BR11 | Одночасні списання з однієї картки не дають «подвійної витрати» | SELECT … FOR UPDATE → 2 сеанси |

## 5. Програмовані об'єкти

- `fn_current_fare(transport_type, at timestamptz)` — SQL-функція, STABLE.
- `fn_card_statement(card, from, to)` — повертає набір рядків (виписка).
- `proc_top_up(card, amount, channel, ref)` — процедура поповнення (транзакційно: top_ups + cards.balance).
- `proc_register_trip(card, validator, at)` — головна операція: блокування картки FOR UPDATE, перевірка статусу, пошук активного проїзного, визначення тарифу з пільгою, списання, запис trips + charges.
- `proc_buy_plan(card, plan)` — купівля тарифного плану.
- Тригери: AFTER — аудит статусу/балансу; BEFORE — перевірка переходу статусу.
- Представлення: `v_card_overview` (картка, власник, баланс, активний проїзний, остання поїздка — DISTINCT ON), `v_daily_revenue` (можна матеріалізоване).

## 6. Ролі

`transit_cashier` (видача карток, поповнення через процедуру), `transit_validator` (лише CALL proc_register_trip), `transit_analyst` (лише SELECT з представлень), власник схеми — адміністратор. Перевіряти від імені кожної ролі (SET ROLE), не від власника.

## 7. Ідеї запитів (≥15)

Поїздки за видами транспорту за період (JOIN + GROUP BY); картки без жодної поїздки (LEFT JOIN / NOT EXISTS); виручка за днями з FILTER (поїздки vs продаж планів); картки з балансом нижче середнього (підзапит); остання поїздка кожної картки (DISTINCT ON); інтервал між поїздками (LAG); накопичувальна сума поповнень (вікно SUM); рейтинг валідаторів за навантаженням (RANK); пікові години (date_trunc + HAVING); частка пільгових поїздок; проїзні, що закінчуються за 3 дні; звірка balance з журналом операцій (CTE); середня кількість поїздок на проїзний; UPSERT поповнення (ON CONFLICT … RETURNING); пасажири з кількома картками.

## 8. Дослідження

- Продуктивність: згенерувати 100 000–1 000 000 поїздок (generate_series, описати спосіб); запити «останні 10 поїздок картки» та «поїздки за інтервал часу»; ANALYZE → EXPLAIN (ANALYZE, BUFFERS) → індекс (card_id, validated_at DESC) / BRIN(validated_at) → повтор; фіксувати перший і повторні запуски. ТІЛЬКИ фактичні виміри.
- Конкурентний доступ: два psql-сеанси одночасно списують з однієї картки; порядок команд, момент блокування, результат.
- Відновлення: pg_dump -Fc → createdb course_restore → pg_restore → перевірка об'єктів, кількості рядків, контрольних запитів, прав.
- NoSQL: Redis як кеш балансу / стоп-лист заблокованих карток для валідаторів (TTL, інвалідація, що є джерелом істини, поведінка при втраті кешу).
