# Порівняння PostgreSQL з Redis для процесу валідації

## Задача, для якої розглядається альтернатива

Найчастіша операція системи — реєстрація поїздки на валідаторі. Їй потрібні дві відповіді за мінімальний час:

1. чи можна пропустити картку (статус, строк дії, «стоп-лист» заблокованих і втрачених);
2. чим оплатити поїздку (чинний проїзний, баланс, пільга).

У PostgreSQL це один виклик `proc_register_trip`, що блокує рядок картки, читає 3–5 таблиць і пише 2–3 рядки. Redis (сховище «ключ–значення» в оперативній пам'яті) часто пропонують як шар, що прискорює саме таке читання. Нижче розглянуто, які дані доречно туди винести, а які — ні.

## Модель даних у Redis

| Ключ | Тип Redis | Вміст | TTL | Джерело |
|---|---|---|---|---|
| `stoplist:cards` | SET | номери карток зі статусом `blocked` / `lost` | без TTL | `cards.status` |
| `card:{card_number}` | HASH | `status`, `valid_until`, `plan_valid_to`, `plan_transport`, `trips_left`, `discount_pct` | 300 с | `cards`, `card_subscriptions`, `passengers` |
| `fare:{transport_code}` | STRING | чинна ціна поїздки | до 00:00 наступної доби | `fares` |

Баланс у Redis **не кешується** як джерело рішення про списання (обґрунтування — нижче).

## Порівняння за вимогами системи

| Критерій | PostgreSQL (поточне рішення) | Redis як кеш |
|---|---|---|
| Структура даних | 12 нормалізованих таблиць, зв'язки через FK, історія операцій | Плоскі ключі й прості структури (SET, HASH); зв'язків і запитів з JOIN немає. Структуру будують під конкретне читання |
| Типові операції | Транзакційне списання + запис журналу; аналітичні запити (Q01–Q18), вікна, агрегати | `SISMEMBER stoplist:cards …` і `HGETALL card:…` — O(1) читання з пам'яті без мережевого обходу кількох таблиць |
| Цілісність | CHECK, UNIQUE, EXCLUDE, FK, тригери (BR01–BR17) гарантуються СУБД | Обмежень немає; узгодженість — відповідальність коду, що оновлює кеш |
| Узгодженість і транзакції | ACID; `FOR UPDATE` усуває подвійне списання (BR11) | `MULTI/EXEC` і Lua-скрипти атомарні в межах одного вузла, але без відкату й без зв'язку з транзакцією PostgreSQL. Дані в кеші можуть відставати від бази |
| Довговічність | WAL: зафіксована транзакція не втрачається | RDB-знімки й AOF зменшують втрати, але кеш за визначенням може бути втрачений; йому не довіряють гроші |
| Масштабування | Вертикальне + репліки для читання; запис — один первинний вузол | Горизонтальне (Redis Cluster), висока пропускна здатність читання |
| Підтримка й відновлення | `pg_dump`/`pg_restore` перевірено ([restore.md](../protocols/restore.md)) | Відновлюється не з резервної копії, а повторним заповненням з PostgreSQL |

## Як оновлюється кеш і що є джерелом істини

- **Джерело істини — PostgreSQL.** Redis містить лише похідні копії, які можна будь-коли видалити й побудувати заново.
- **Стоп-лист.** Оновлюється подією, а не за TTL: заблокована картка має перестати проходити одразу. У PostgreSQL це природно лягає на наявний тригер аудиту статусу: AFTER-тригер виконує `pg_notify('card_status', card_number || ':' || new_status)`. Сервіс-слухач (`LISTEN card_status`) робить `SADD`/`SREM stoplist:cards`. Оскільки `NOTIFY` доставляється лише після COMMIT, кеш не побачить скасованих змін.
- **Картка й проїзний (`card:{number}`).** Інвалідація при зміні (`DEL card:{number}` після купівлі проїзного, зміни пільги чи статусу) плюс TTL 300 с як страховка від пропущеної події.
- **Тариф.** TTL до кінця доби: межі тарифів у `fares` — календарні дати (BR06).

## Поведінка при втраті кешу

| Ситуація | Наслідок | Дія |
|---|---|---|
| Перезапуск Redis без збереження | порожній стоп-лист — **небезпечно**: заблоковані картки пройдуть | при старті сервіс повністю перебудовує стоп-лист: `SELECT card_number FROM cards WHERE status <> 'active'` (у тестових даних — 2 картки; за великих обсягів — частковий індекс `WHERE status <> 'active'`) і лише після цього відкриває валідацію |
| Відсутній ключ `card:{…}` | промах кешу | читання з PostgreSQL і запис у Redis (cache-aside) |
| Redis недоступний | — | валідатор працює напряму через `proc_register_trip`; кеш — оптимізація, а не умова роботи |

## Чому баланс і списання залишаються в PostgreSQL

Атомарне зменшення балансу в Redis (`DECRBY` або Lua-скрипт з перевіркою) технічно можливе й швидке, але:

- журнал `charges` і баланс мають змінюватися **разом** (FR05, звірка — 0 розбіжностей). Дві системи без розподіленої транзакції цього не гарантують: після збою між записами гроші списано в одній системі й не зафіксовано в іншій;
- правило «пересадка безкоштовна, якщо платна поїздка була < 60 хв тому на іншому валідаторі» (BR10) потребує історії поїздок і унікальності `transfer_from_trip_id`. У Redis це довелося б відтворювати вручну;
- блокування `FOR UPDATE` уже розв'язує конкурентне списання (BR11), а вимірювання показали, що основні запити працюють за одиниці мілісекунд ([explain_before_after.md](../protocols/explain_before_after.md)).

## Висновок

Redis доречний як **допоміжний шар для валідаторів**: стоп-лист заблокованих карток і кеш стану картки/проїзного. Це запити «так/ні» з дуже високою частотою, де помилкову відмову можна виправити повторним читанням з бази. Умова доцільності — тисячі валідацій за секунду або віддалені валідатори з повільним каналом до бази. За обсягів навчального проєкту виграш не обґрунтований: PostgreSQL відповідає за мілісекунди, а кеш додає код синхронізації й ризик розбіжностей. Гроші, журнали операцій, правила цілісності й аналітика залишаються в PostgreSQL. Обмеження рішення з Redis: можливе відставання кешу до спрацювання інвалідації і небезпека «порожнього стоп-листа» після втрати даних, яку закриває обов'язкова перебудова при старті.
