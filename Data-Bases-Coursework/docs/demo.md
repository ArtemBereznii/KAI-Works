# Демонстрація на захисті (≈5 хв)

Сценарій — [sql/demo.sql](../sql/demo.sql). Він іде в одній транзакції з `ROLLBACK` наприкінці, тож дані не змінюються і демонстрацію можна повторювати скільки завгодно. Очікувані помилки не зупиняють сценарій (`ON_ERROR_ROLLBACK on` відкочує лише невдалий оператор).

## Підготовка (до захисту)

```sh
docker compose up -d --wait
./run_all.sh                       # чистий стан: схема, дані, запити, 33 тести
```

Запуск демонстрації — psql з паузою «Enter — далі» між кроками:

```sh
docker compose exec db psql -U postgres -d transit_db -f /work/sql/demo.sql
```

Перевірити сценарій без пауз: додати `-v nopause=1`.

## Кроки й що казати

| Крок | Що видно | Що сказати |
|---|---|---|
| 1. Структура | `\dt transit.*` — 12 таблиць; зовнішні ключі `cards`, `trips`, `charges` | Усі FK — `ON DELETE RESTRICT`, історія не губиться; `trips` посилається сама на себе — пересадка |
| 2. Операція користувача | Касир видає картку 4555…01 і поповнює на 100; повтор платежу `DEMO-001` ігнорується (BR09). Валідатор: автобус −20.00, метро через 30 хв — `transfer`, той самий валідатор ще раз — −25.00. Огляд картки й виписка | Усе через процедури від імені ролей; баланс 55.00 збігається з випискою |
| 3. Аналітичний запит | Від імені аналітика: поїздки метро за годинами з пересадками й виручкою (`v_trip_facts`, FILTER, HAVING) | Аналітик бачить лише знеособлене представлення |
| 4. Відмови | 5000.01 грн → `23514`; другий проїзний на той самий час → `23P01`; lost → active → BR05; видалення картки з історією → `23001`; аналітик читає `passengers` → `42501` | Правила тримає СУБД, а не застосунок; кожен код є в тестах T05, T18, T21, T26, T29 |
| 5. Тригер | Блокування картки: запис в історії з `changed_by = transit_cashier` і причиною; поїздка заблокованою карткою → BR04 | BEFORE-тригер перевіряє перехід, AFTER-тригер пише аудит; виконавця визначає `fn_actor()`, бо в SECURITY DEFINER `current_user` — власник |
| 6. Транзакція й швидкодія | Поїздка з нульовим балансом → BR02, поїздок 0, баланс 0.00; звірка балансу — 0 розбіжностей; `EXPLAIN` — `Index Scan Backward` по `trips_card_time_uq` | Процедура атомарна; індекс уже створило обмеження UNIQUE (BR15) |

## Зміна запиту на місці

Крок 3 параметризовано змінними psql, тож запит можна змінити, не переписуючи його. Після кроку 3 (або в окремому сеансі після `SET search_path = transit;`):

```sql
\set transport 'bus'        -- bus, trolleybus, tram, metro
\set min_trips 100
SET ROLE transit_analyst;
SELECT trip_hour, count(*), count(*) FILTER (WHERE payment_method = 'transfer') AS transfers, sum(amount)
FROM v_trip_facts
WHERE transport_type = :'transport'
GROUP BY trip_hour HAVING count(*) >= :min_trips
ORDER BY 2 DESC;
RESET ROLE;
```

Інші типові прохання комісії і як їх виконати:

- **«Покажіть лише листопад»**: додати `AND trip_date >= DATE '2026-11-01'` у `WHERE`.
- **«Групуйте за днями, а не годинами»**: замінити `trip_hour` на `trip_date` у `SELECT` і `GROUP BY`.
- **«Частка пільгових поїздок»**: додати `round(100.0 * count(*) FILTER (WHERE is_privileged) / count(*), 1)`.
- **«Хто з пасажирів не має карток»**: це запит Q03 з `07_queries.sql` (`LEFT JOIN … IS NULL`), виконувати від власника схеми, бо аналітику таблиця `passengers` недоступна.
